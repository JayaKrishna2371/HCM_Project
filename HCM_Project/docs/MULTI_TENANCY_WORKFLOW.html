1 · What this is

A single deployment that securely serves many isolated Business Units (tenants). Identity is verified against Active Directory over LDAP; the database is the source of truth for which tenant a user belongs to and what they may do. Every API call is scoped to the caller's tenant.

DecisionChoiceWhy
Data isolationShared DB + shared schema + tenant_id (row-level)Scales to many BUs; one schema; central enforcement
AuthenticationLDAP / Active Directory bindNo passwords stored in the app
AuthorizationDB-managed roles & permissionsAdmins assign roles; clean audit; no AD-group sprawl
Tenant contextJWT tenant_id (+ X-Tenant-Id for super-admin switch)Identity-based, single URL — not subdomain-based
Tenant nestingNone (flat tenants)Simpler isolation; per requirement

7 · Provisioning lifecycle (who creates whom)

1
SUPER_ADMIN (seeded at startup) logs in — recognised via SUPER_ADMIN_USERNAME.
2
Onboards a tenant (Tenant Management): code, name, login type, optional own-LDAP fields.
3
Creates a TENANT_ADMIN for that tenant (User Management) — by username; tenant bound automatically.
4
TENANT_ADMIN logs in (LDAP) — sees Administration scoped to their tenant only.
5
Creates tenant USERS (role bound to their own tenant; cannot grant SUPER_ADMIN).
6
USER logs in — dashboard + own-tenant data only; no Administration menu.
